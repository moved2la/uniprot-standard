| D14 | 2026-09-10 | The Gene Ontology lookup name for the Tier 2 seed word "sarcoplasmic" (D4) is the noun **`sarcoplasm`**, matched the same way. | As D13. |

| D16 | 2026-09-10 | **Every entry uses its canonical UniProt sequence.** No isoform is selected by any rule. | D17 | 2026-09-10 | **No fiber-type field** in the protein set. | Fiber type is a Layer B quantity (per-fiber-type abundance, including ~0), obtained from the proteomics dataset directly. A field parsed from UniProt free text would be a hand-written string map producing redundant information. |

| D19 | 2026-09-10 | **Processing rule** reads the UniProt `Chain` feature: exactly one → master range; none → whole sequence, logged; several → *(see D24)*; non-exact position → flag. | The Chain feature is the structured statement of the mature chain. | D20 | 2026-09-10 | The pool is defined as the **union of one UniProt query per subtree term**; UniProt's own term-level query is run as a check and any difference is flagged. | The definition must not depend on how UniProt's search index expands a term. | D21 | 2026-09-10 | A surprising member of a subtree or pool is a **flag closed in Step 3 against measurement**, never a reason to re-pick the term. | The category must remain derived. |

| D23 | 2026-09-10 | Nothing from the first repository is inherited. All code is rewritten from the specification in the Step 1 handoff. | `PROVENANCE.md`: a previous version of the repository is not a source. |
| D24 | 2026-09-11 | **R2d:** when an entry has more than one exact `Chain` feature, the master molecule is the **union of their ranges**. Such entries are listed in `outputs/multi_chain_entries.tsv`; they are not flags. | The first run raised 7 flags, all of this kind, in two shapes: a precursor cleaved into two products that both persist, and stepwise N-terminal processing recorded as an intermediate-form chain plus a final chain. Closing them individually would mean seven decisions and, for the second shape, a judgment read from free-text chain descriptions. The union is field-based, deterministic, and keeps every residue that is part of some mature product; where it retains a residue the final product lacks, the processing-delta table states the size of the effect. |
| D25 | 2026-09-11 | `data/uniprot_verification.ini` is renamed **`data/uniprot_sequences.ini`**, and the stage that writes it, `verify_accessions.py`, is renamed **`fetch_sequences.py`** (log files follow the stage name). Content is unchanged; only the file's own header line and the references to it were edited. | The file is where the canonical sequences live; verification (the MD5 check) is a property of how it was made, not what it contains. The name was misleading a reader into thinking the sequences lived elsewhere. Renamed before the composition engine became a second reader of the old name. |
| D26 | 2026-09-11 | **Amino acid symbols are parsed from their defining source and masses are fetched from PubChem, both by code.** The hand-written input is `config/composition_decisions.ini`, holding only: the URL of the IUBMB web copy of Table 1 of IUPAC-IUB JCBN *Nomenclature and Symbolism for Amino Acids and Peptides. Recommendations 1983* (Pure Appl. Chem. 1984, 56(5), 595–624), the PubChem PUG REST endpoint, and the query rule. `fetch_amino_acid_masses.py` downloads the table page, hashes it, parses every `<trivial name> <three-letter> <one-letter>` row and stops unless exactly the twenty standard letters are found once each; it then queries PubChem by name — the chiral prefix `L-` joined to the trivial name (Table 1 footnote a; 3AA-14.5), falling back to the bare trivial name when PubChem has no compound under the prefixed name, and recording per row which name resolved — and records CID, molecular formula, IUPAC name, and `MolecularWeight` as served, deriving residue mass = free mass − water. | Everything by code unless absolutely necessary: the source of the one-letter code is machine-readable, so the code reads it, and the only author-written content is two URLs and one rule — the same shape as the ontology URL (D15). Options not taken: a transcribed twenty-row seed checked against the page (rejected: a transcription step); a library's built-in table (provenance one hop removed); formula × atomic weights (more machinery than the precision needed). PubChem serves `MolecularWeight` to two decimals; that precision is recorded in the table header and stated in methods. |
| D27 | 2026-09-11 | **Cysteine is reported as cysteine, at the free-cysteine mass, and cysteine and methionine are separate columns of the standard.** USDA tables report "cystine"; the mapping between the two conventions (2 × cysteine − 2 H per cystine) is handled where USDA data are ingested, not here. | A labelling and mass-convention question, not a nutritional one. Keeping the two sulfur amino acids as separate columns lets the Match Rate step combine, score separately, or drop either without the standard pre-deciding it. The nutritional question — whether Match Rate may ignore cysteine on the grounds that methionine is sufficient — is deferred to the Match Rate step (handoff 02, Deferred / raised). |
| D28 | 2026-09-11 | **Post-translational modifications are not modelled; their mass is disclosed.** The composition engine counts sequence letters, so a modified residue is counted as its unmodified amino acid. `ptm_disclosure.py` reads every `Modified residue`, `Lipidation`, `Glycosylation`, `Cross-link`, and `Disulfide bond` feature from the raw entry JSON, looks the description's first clause up in UniProt's PTM vocabulary (`ptmlist.txt`, fetched and hashed), takes the vocabulary's average mass difference where one is given, prices an intrachain disulfide bond as −H₂ (PubChem), counts everything else without a mass and lists it, excludes sites outside the master molecule from the sums, and reports per entry the summed delta as a fraction of molecular weight and the set-wide maximum. No decision is attached to the number. | Disclose rather than adjudicate, as for isoforms (D16). Counting a modified residue as its unmodified amino acid is what a dietary standard needs — the residue the diet supplied is the unmodified one — but that argument and its citations belong to the paper step, not to the code; the code only reports the size of what is not modelled. |
| D29 | 2026-09-11 | **Output shape.** `outputs/composition/amino_acid_composition_per_protein.tsv` has one row per accession per segment set (`master`, `metabolic`); tier is carried as the list `accessions.ini` gives (`1`, `2`, or `1;2`), not split into rows; both mass conventions are written as fractions (g/100 g = 100 × fraction, not written separately); files are TSV like the rest of the repository; no per-accession files. Fractions are written with 10 significant digits, sums and molecular weights with 4 decimals. | Composition does not depend on tier; Step 3 splits at weighting time. One wide table is what Step 3 and Step 4 read. Fixed digit counts make the file byte-identical across machines. |
| D30 | 2026-09-11 | **Hydrolysis-sensitive residues (tryptophan, cysteine, methionine, serine, threonine, asparagine, glutamine) are reported at full sequence value.** | The sequence is exact; nothing degrades in arithmetic. Where laboratory amino acid analysis diverges from these values is the subject of the validation step. |
